Why This Matters

For eleven sessions you have been given data structures and told what they cost. ArrayList.get(i) is O(1). A HashMap lookup is O(1). A queue should be a Deque, not a Stack. All true, all memorised, and none of it is knowledge you can use under pressure — because when a lookup is mysteriously slow in your own code, the sentence “a hash map is O(1)” gives you nothing to look at.

The difference between knowing a fact and being able to use it is having built the thing once. After today, “O(1)” stops being a claim you accept and becomes a sentence about a line of code you wrote: one array read, one addition, one mask. And when something is slow, you will have the one question that actually finds the problem — what does this key's hashCode() return in binary? — instead of a shrug.

There is a second reason, and it is the honest one. Everyone in this room will read far more data-structure code than they write. You will be handed a cache somebody wrote by hand, a queue with an off-by-one in its wrap arithmetic, a class whose equals and hashCode disagree. Being able to read those in five minutes rather than five hours is a professional skill, and it is not taught by using ArrayList.

🎭
Analogy — driving, then opening the bonnet You have been driving for eleven weeks, and driving well: you know which pedal does what and you can park. Today you open the bonnet. Nothing you learn will change how you drive — you will still use ArrayList on Monday, exactly as you should. Using a tool and understanding it are different skills, and only one of them can be borrowed.

Part 1 of 9 Why Build One When the JDK Ships One?

Fair question, and it deserves a straight answer before you write a line of code. The JDK's structures are better than anything you will write today: they are faster, they have been tested by millions of programs for thirty years, and one of them was written by people who have forgotten more about hash tables than this course will ever teach you. You are not going to replace them. Ever. Everything you build today gets deleted at the end of Part 9, and that is not a joke — it is the lesson.

So why write them? Because there are three questions the JDK's classes cannot answer for you, and all three of them come up in real work:

  1. “Why is this slow?” A HashMap that has stopped being a map looks exactly like a HashMap that is working. It returns the right answers. The only way to tell the difference is to know what is inside it — and the only way to know that without taking somebody's word for it is to have built one.
  2. “What does this number mean?” O(1), O(log n), “amortised”, “load factor 0.75”. These are all descriptions of code you are about to write. A definition you memorised decays; a measurement you made yourself does not.
  3. “What is this code doing?” Which is the question you will actually be paid to answer. Somebody's hand-rolled ring buffer, somebody's open-addressed table, somebody's linked list with a bug in the middle — you will meet all three, and the shape of the code will be familiar on sight if you have written one yourself.
✦
Key Point You build the model, not the product. What you write today holds a few hundred items and is not thread-safe, not generic, and not as fast as the JDK's. That is fine, because nobody is going to use it. The thing you are building is the explanation — and an explanation you can run, break and count is worth ten you can only recite.

The three structures are chosen because each one teaches one idea and nothing else:

  • A dynamic array (IntList) — an array that cannot grow, wrapped in a class that replaces it when it fills. One idea: amortised cost.
  • A hash map (SimpleMap) — an array of short chains, with a mask choosing the bucket. One idea: spread, and what happens when you do not have it.
  • A ring-buffer deque (RingBuffer) — one array, two indexes, one modulo. One idea: the front of a queue is a position, not a place.

They are also the three the JDK's ArrayList, HashMap and ArrayDeque are built on, which is where Part 8 lands: once you have your own, the JDK's stop being magic and become the same design with thirty years of polish.

Part 2 of 9 Your Own Dynamic Array

Session 1 told you that ArrayList is backed by an array and that get(i) is O(1). Both halves of that sentence matter, and the second one is easy to take on trust because it sounds like good news. Here is the problem it hides: a Java array cannot get longer. new int[4] is four slots, forever. So a list that appears to grow is not growing anything — it is throwing the array away and building a bigger one, copying every element across, every so often.

The whole of IntList is three fields and four short methods. Every line of it exists to make one of these decisions: 

package com.aptech.s11b.ds;

/**
 * A growable list of ints, built by hand.
 *
 * This is the whole of ArrayList's core idea and nothing else: an array that is usually bigger
 * than the data, plus a count of how much of it is used. When the array fills up, a bigger one
 * is allocated and everything is copied across. That copy is the only expensive operation, and
 * doubling is what makes it rare.
 *
 * The point of writing it is that nothing here is magic. ArrayList.get(i) is O(1) because it is
 * the line {@code return data[index];} below - one array read, whatever the size.
 *
 * {@code copies} counts the element copies performed by growth, so the cost of add() can be
 * measured by counting rather than by timing. A count is deterministic; a millisecond reading
 * is noise plus truth.
 */
public class IntList {

    private int[] data;
    private int size;
    private int copies;
    private long reads;

    /** A list with room for four, which is where the doubling table on the page starts. */
    public IntList() {
        this(4);
    }

    public IntList(int initialCapacity) {
        data = new int[Math.max(1, initialCapacity)];
    }

    /** How many elements are actually stored. */
    public int size() {
        return size;
    }

    /** How much room the backing array has. Always >= size. */
    public int capacity() {
        return data.length;
    }

    /** Total element copies performed by every grow() so far. */
    public int copies() {
        return copies;
    }

    /** How many array reads get() has performed. E02 compares this with ArrayList's count. */
    public long reads() {
        return reads;
    }

    /** Appends a value, growing the array first if it is full. */
    public void add(int value) {
        if (size == data.length) {
            grow();
        }
        data[size++] = value;
    }

    /** One array read. This is the line that makes get() O(1). */
    public int get(int index) {
        checkIndex(index);
        reads++;
        return data[index];
    }

    public void set(int index, int value) {
        checkIndex(index);
        data[index] = value;
    }

    /** Up to size reads: the worst case, and the reason contains() is O(n). */
    public int indexOf(int value) {
        for (int i = 0; i < size; i++) {
            if (data[i] == value) {
                return i;
            }
        }
        return -1;
    }

    public boolean contains(int value) {
        return indexOf(value) >= 0;
    }

    /** Removes one element and shifts the rest left, which is the O(n) part. */
    public int removeAt(int index) {
        checkIndex(index);
        int removed = data[index];
        System.arraycopy(data, index + 1, data, index, size - index - 1);
        data[--size] = 0;
        return removed;
    }

    /**
     * The whole trick, in six lines: allocate twice the room, copy the live elements, throw the
     * old array away. Every element is copied once per growth, so the total for n adds is about
     * n + n/2 + n/4 + ... which is less than 2n - that is why add() is called O(1) on average.
     */
    private void grow() {
        int[] bigger = new int[data.length * 2];
        System.arraycopy(data, 0, bigger, 0, size);
        copies += size;
        data = bigger;
    }

    private void checkIndex(int index) {
        if (index < 0 || index >= size) {
            throw new IndexOutOfBoundsException("Index " + index + " out of bounds for size " + size);
        }
    }
}

Read add() once more, because it is the entire design in three lines: if the array is full, make room first; then store. That is the trade. The list keeps an array that is allowed to be partly empty, and pays for the wasted slots by never having to move an element except when it grows.

Key Point Doubling is not a tuning detail — it is the algorithm. A growth copies everything already stored, so what matters is how many times you grow. Doubling makes the gaps between growths double too, so n adds grow about log₂n times. Growing by a fixed amount keeps the gaps the same size forever, so you grow about n/10 times — and the difference between “less than 2n copies” and “499,900 copies” is one line.

Part 3 of 9 Measuring It Without a Clock

Before the hash map, one detour — because you are about to make claims about cost, and the obvious way to check a claim about cost is wrong. The obvious way is a stopwatch. It is also the reason people argue about performance for a living. Run the same loop twice on the same machine and you get two different numbers: the JIT has warmed up the second time, or a background update started in between, or the laptop throttled. A millisecond reading is the truth plus noise.

There is a better instrument, and you have already used it twice on this page without noticing: count the work instead of timing it. Every operation that matters here bottoms out in the same physical act — reading one slot of an array. Count those and you get a number that is identical on your laptop, on mine, and on the machine that runs this in three years' time, because nothing about it depends on how fast the hardware is. What the count measures is the shape of the work, which is what O(1) and O(n) have always been about.

The catch is that you can only count a structure that counts itself. So the program below does something worth noticing before you read it: it subclasses ArrayList and overrides get() purely to count. That is the only reason the JDK's list can be put in the same table as ours — both sides are now counting the same thing.

Three things in that output are worth keeping, and none of them needed a stopwatch.

Three gets cost three reads, at every size. Ten elements, a thousand, a hundred thousand — the number in that column never moves. That is what O(1) looks like when you stop describing it and start counting it: not “fast”, but unchanging.

Finding the last element costs n reads, and finding nothing costs n too. That is the expensive half of a list, and it is the reason the next part exists: a scan is linear because it has no idea where to look. A lookup that does know where to look can beat it — and that is the entire promise of hashing.

IntList and ArrayList do the same work because they are the same design, and now you have evidence rather than a claim. Every cost figure in this session — copies, comparisons, reads, element moves — is a counter inside the class, printed by the program, identical on every run. If you take one habit from today, take this one: when a claim about performance matters, find something to count.

Part 4 of 9 Your Own Hash Map: Buckets and Chains

You have used HashMap since Session 1 and you already know the contract from Session 10: override hashCode with equals, because a map uses the first to find the bucket and the second to confirm the key. What you have never seen is the machine in between — and it is smaller than you would expect. Three parts:

  1. A bucket array. Not an array of values — an array of short lists, because two different keys are allowed to want the same slot.
  2. A mask. hash & (buckets.length - 1) turns any int into a legal bucket number, without a division and without a negative index.
  3. A chain per bucket. Colliding keys are stored one behind another; a lookup walks the chain comparing keys with equals().

That is the whole structure. Everything else in a real hash map — resizing, treeifying, concurrency — is a fix for a problem this design creates. Here is ours, and the two methods that carry the idea: 

    public void put(Object key, int value) {
        int hash = hashOf(key);
        int index = hash & (buckets.length - 1);
        for (Node n = buckets[index]; n != null; n = n.next) {
            probes++;
            if (n.hash == hash && n.key.equals(key)) {
                n.value = value;
                return;
            }
        }
        buckets[index] = new Node(key, hash, value, buckets[index]);
        size++;
        if (size > buckets.length * LOAD_FACTOR) {
            rehash();
        }
    }

    /** The value, or null when the key is not in the map. */
    public Integer get(Object key) {
        int hash = hashOf(key);
        int index = hash & (buckets.length - 1);
        for (Node n = buckets[index]; n != null; n = n.next) {
            probes++;
            if (n.hash == hash && n.key.equals(key)) {
                return n.value;
            }
        }
        return null;
    }

Two details in there are easy to skate past and both matter. First, the chain stores the hash alongside the key, and compares n.hash == hash before calling n.key.equals(key) — an int comparison is cheaper than a method call, so it filters out almost every non-matching node for free. Second, the anchor of each chain is hashOf(key) = h ^ (h >>> 16), which folds the top half of the hash into the bottom half so the low bits — the only bits the mask reads — still carry information.

That tie-breaking is section 3's problem, and Java 8 added the fix. Everything else is what you have just written.

Follow one lookup all the way down. get(33) hashes 33, masks it to bucket 1, finds a chain of two there, compares the stored hash, calls equals on the first node and returns — one comparison, because 33 was added after 25 and every new key goes on the front of its chain. Its neighbour get(25) costs two, because 25 is behind it. Both beat the six comparisons a scan of the whole map would need — and with a hundred keys in the map they would still cost about the same, because there would be a hundred buckets and the chains would stay short. That is the O(1): it comes from the spread, not from luck.

Which raises the question the whole structure rests on — and section 3 of the output answers it. Six keys chosen as 0, 8, 16, 24, 32, 40 all leave the same remainder, so all six land in bucket 0. The map is still correct: every key is found, nothing throws. But get(0) now costs six comparisons, and the class did not change. The keys chose the bucket.

Section 4 is the last piece of the machine, and it is the same idea as Part 2 wearing different clothes. As keys accumulate, chains get longer and lookups drift back towards a scan. So the table watches its own fullness and doubles before things get bad — when the count of keys passes three-quarters of the bucket count. Every key has to be moved into the bigger table, because the mask changed and the bucket a key wants is not the bucket it is in. That is rehashing, and it is precisely the growth you counted in E01: rare, expensive when it comes, and cheaper on average than the alternative.

✦
Key Point A hash map is an array of chains plus a rule for choosing a chain. The array gives it the O(1); the chains give it correctness when two keys disagree about nothing except which slot they want. Every property you care about — speed, memory, the behaviour when a lookup misses — follows from those two pieces and how full the array is allowed to get. Nothing else is hidden, and that is the point of building it once by hand.

Part 6 of 9 Your Own Deque — the Ring Buffer

One more structure, and this one exists to fix an annoyance you may have already felt. Take a list and treat it as a queue: add() to the back, remove(0) from the front. It works, and it is a trap. Removing the first element of a list means moving every other element down one slot — one removal, n moves. Ten thousand jobs through a thousand-element queue is ten million element moves to accomplish nothing at all.

The ring buffer's answer is to stop moving things. Keep one array, and instead of shifting elements towards the front, move the front. head is the slot the next element comes out of; tail is the slot the next element goes into; and when either reaches the end of the array it wraps to the start with one %. The slots the queue has already passed are free and get reused. Nothing is ever copied, ever. 

    /** Adds to the back. The one line that makes it a ring is the tail arithmetic. */
    public void push(String value) {
        if (isFull()) {
            throw new IllegalStateException("ring buffer is full: " + capacity() + " slots");
        }
        data[tail] = value;
        tail = (tail + 1) % data.length;
        size++;
    }

    /** Removes from the back - the newest. Use with push() and this is a stack. */
    public String pop() {
        checkNotEmpty();
        tail = (tail - 1 + data.length) % data.length;
        String value = data[tail];
        data[tail] = null;
        size--;
        return value;
    }

    /** Removes from the front - the oldest. Use with push() and this is a queue. */
    public String poll() {
        checkNotEmpty();
        String value = data[head];
        data[head] = null;
        head = (head + 1) % data.length;
        size--;
        return value;
    }

Look at how little there is. push writes at tail and advances it; poll reads at head and advances it; pop steps tail backwards and reads. Every one of them is a read or a write plus one addition — no loop, no shift, no matter how many elements are stored. And notice that the same class is a stack and a queue depending only on which end you take from. That is ArrayDeque: one class, both jobs, because the ring genuinely does not care.

The one thing that needs care is telling full apart from empty. With head and tail alone, both states look identical — the two indexes are equal — which is the classic ring-buffer bug. That is what the size field is for, and it is why isFull() is size == data.length rather than an index comparison.

One array, no shifting, no copying. Two indexes move, and wrap. 1. The two slots they passed are free again, and nothing was copied to free them. 2. Three pushes, and the ring is in use push(a), push(b), push(c) slot 2=a, slot 3=b, slot 4=c head=2 tail=5 size=3 reading oldest first: [a, b, c] 3. Four more, and tail runs off the end and comes back push(d), push(e), push(f), push(g) slot 2=a, slot 3=b, slot 4=c, slot 5=d, slot 6=e, slot 7=f, slot 0=g head=2 tail=1 size=7 reading oldest first: [a, b, c, d, e, f, g] g went into slot 0 - the front of the array - and it is the NEWEST element. Slot order and queue order have nothing to do with each other. tail became (7 + 1) % 8 = 0, and that one line is the whole ring. 4. The same object, used two ways as a queue: push x3, then poll() -> first (the oldest, which is what a queue gives you) as a stack: push x3, then pop() -> third (the newest, which is what a stack gives you) push()/poll() is a queue. push()/pop() is a stack. One class, because the ring does not care which end you take from. 5. A thousand turns, and the array never grows 1000 pushes and 1000 polls later: capacity 8, size 0, head 0, tail 0 Capacity 8 throughout. Compare that with IntList, which replaces its array over and over. Neither is better - they are built for different jobs, and a queue is this one's job. 6. ArrayDeque is this, with the edges filed off as a stack: push, push -> [top, bottom] ; pop -> top as a queue: addLast x3 -> [first, second, third] ; pollFirst -> first ArrayDeque is a ring buffer that grows by doubling when it fills, is not synchronized, and refuses nulls. Section 3 of the output is the wrap, and it is worth following the arithmetic by hand: g goes into slot 7, and then tail = (7 + 1) % 8 = 0. The next element would land at the front of the array. That single line is the entire difference between a ring buffer and a list — and the reason the same eight slots can serve a queue that runs all day.

Section 5 is the payoff, and it is the honest comparison Part 2 set up. A thousand pushes and a thousand polls through a ring of capacity 8: capacity 8 at the end, exactly as at the start, and the array was never replaced. An IntList doing the same job would have grown to over a thousand slots and copied thousands of elements to get there. Neither structure is better — a growable array is wrong for a queue, and a fixed ring is wrong for a growing list. They are built for different jobs, and a queue is this one's job.

Part 8 of 9 Why the JDK's Versions Won

Both sides passed. So why does every Java program on earth use ArrayList and not something a student wrote this morning? Not because of anything the suite could see. The suite compares behaviour, and the differences that matter here are not behavioural — they are engineering. Six of them, and you are now equipped to understand every one:

  1. It is generic, so it holds anything. Our IntList holds int and our SimpleMap goes from String to int. Writing a second list for String would mean copying the whole file and changing one type. Generics — Session 6 — exist to make that one file.
  2. It iterates, safely and fast. There is no way to walk our structures with a for-each, because they do not implement Iterable. Inside, a hand-written structure is also a layout: ours keeps values in a plain array, and the JDK's keeps Integer references, so every element of an ArrayList<Integer> is a boxed object on the heap. That is the boxing trade in the table above, and it is real: an int[] of a million numbers is four megabytes; an ArrayList<Integer> of the same million is the array plus a million objects.
  3. Its growth policy is tuned and documented as unspecified. This is the honest one. ArrayList grows by roughly 1.5×, not 2×, and its javadoc says the growth policy is unspecified — which is a promise that you must not depend on the exact capacity, only on the amortised cost. That is a deliberate boundary drawn around an implementation detail, and it is a habit worth copying.
  4. Its map handles the bad case you are not allowed to ignore. Java 8 added treeified bins: when one bucket's chain grows past eight entries, that chain is converted into a balanced tree, and a lookup in it costs O(log n) instead of O(n). That is Part 5's disaster — twenty-one comparisons and rising — turned into a case that is merely worse, not catastrophic. The JDK's own javadoc says using many keys with the same hashCode() is a sure way to slow down any hash table; the treeification is the fix, and when the keys are Comparable the tree can also use their natural order to break ties.
  5. It knows it is being modified while you look at it. Remember Session 11's Enumeration, which notices nothing? A modern collection's iterator is fail-fast: modify the collection while a loop is walking it and the next next() throws ConcurrentModificationException rather than quietly skipping an element. Our structures have no iterators at all, so they cannot notice — which means the bug would surface later, somewhere else, as a wrong number.
  6. It has been wrong and been fixed, in public, for thirty years. Every one of those features is a bug somebody found in production. That is the part you cannot write this morning.

Common Mistakes

Every one of these is something SelfCheck is designed to catch, so the safest way to read this section is as a translation table. The symptom is real output; the cause is what the code is doing; the fix is one line.

  1. Copying into an array of the same size. grow() writes data = new int[size] instead of new int[size * 2], or reuses the old array. add() calls grow(), comes back, and stores at data[size] — one slot past the end of an array that is still full. Symptom: capacity should have doubled from 4 to 8, it was 4 on the way in, and an ArrayIndexOutOfBoundsException if the check did not stop you first. Fix: the new array is data.length * 2, and the old one is dropped.
  2. Counting the wrong thing in copies. The counter is the number of elements moved, not the new capacity and not the number of growths. Symptom: one growth of a full four-element array copies 4 elements, copies() said 0 (forgotten) or … said 8 (counting the new length). Fix: copies += size; after the copy — it is the live element count before the growth, which is exactly the old capacity at that moment.
  3. Bounds-checking against capacity instead of size. get() written as if (index >= data.length) accepts an index into an unused slot and returns the 0 sitting there — a value that was never added, delivered as if it were. Symptom: get(3) on a list of three must throw IndexOutOfBoundsException. Fix: the legal range is 0 .. size - 1. The capacity is how much room there is, not how much list there is.
  4. Putting a second node instead of replacing the first. put() walks the chain, finds a match, and adds the new node anyway instead of updating and returning. Symptom: putting the same key twice must replace, not add, and one key put twice is still one key, size said 2. Fix: a match means change and leave. That early return is the whole difference between a map and a list of pairs.
  5. Rehashing one key too late. The rule is size > buckets.length * 0.75, checked after the new key is stored, and the boundary is strict — six keys in eight buckets is exactly three-quarters and therefore not past it. Symptom: 6 keys in 8 buckets is exactly three-quarters full - not past it - so no rehash yet, or the mirror image, the 7th key takes it past 0.75, so the table must double to 16. Fix: >, not >=, and check after the increment.
  6. A mask that is not a mask. Writing hash % buckets.length works, so this one hides — until a hash is negative, when % returns a negative index and the array access throws. hash & (buckets.length - 1) is correct for every int precisely because the length is a power of two. Symptom: an ArrayIndexOutOfBoundsException naming a negative index, usually only for a particular key. Fix: use the mask, and keep the bucket count a power of two so the mask keeps working.
  7. Walking the array in slot order in toString(). The one that catches almost everybody. After a wrap, slot order and queue order are different lists, so a loop from 0 to data.length prints the elements in the wrong order — or prints null for the free slots as well. Symptom: the contents must still read oldest-first, they printed as [null, a, null, null]. Fix: walk the queue, not the array: data[(head + i) % data.length] for i from 0 to size - 1.
  8. Stepping tail backwards with a plain modulo. tail = (tail - 1) % data.length gives -1 when tail is 0 — Java's % keeps the sign of the left operand, so the result is negative, not wrapped. Symptom: the first pop() after a wrap throws with a negative index. Fix: add the length before taking the modulo: (tail - 1 + data.length) % data.length. Shifting the value into the positive range first is the same trick every circular calculation needs.
  9. Returning null from an empty buffer instead of refusing. It compiles, it never throws, and it hands the caller a value that looks like data. Symptom: poll() on an empty buffer must throw IllegalStateException. Fix: check the size first and throw. E06 prints the alternative the JDK chose (NoSuchElementException) — either is honest; silence is not.
  10. Confusing size == 0 with head == tail. The classic ring-buffer bug, and it is invisible until the buffer is exactly full. Symptom: two elements in two slots must be full. Fix: that is what the size field is for. isEmpty() is size == 0; isFull() is size == data.length. With the two indexes alone, full and empty are the same state, and no amount of cleverness fixes that.

Why does the course count array reads instead of timing the operations?
C. A count of array reads is identical on every machine and every run, and it shows how the work grows — which is what O(1) and O(n) describe. A stopwatch measures how fast your laptop is today, plus the truth.

A new SimpleMap has eight buckets. Which bucket does the key 33 go into, and why?
A. hash & (buckets.length - 1) is 33 & 7 = 1. Because the length is a power of two, the mask and the remainder agree for positive values — which is why you can check a hash map's behaviour on paper. Nothing in a hash map looks for an empty bucket: that would cost a scan, which is the thing hashing exists to avoid.

Six keys all have hashCode() returning 1. Their equals() is correct. What happens?

📋 Cheat Sheet

The dynamic array

  • get(i) → return data[i]; — 1 array read, O(1) at every size.
  • add(x) → store, or grow first if full — O(1) amortised.
  • grow() → data = new int[data.length * 2]; then copy — O(n), about log₂n times.
  • Scan for x → up to n reads. O(n).
  • removeAt(0) → shifts everything — O(n). This is why a list is a bad queue.
  • The rule: double, never a fixed step. What matters is how often you grow.

The hash map: six steps

  • 1. Spread → h ^ (h >>> 16). The mask reads only the low bits, so fold the high ones down.
  • 2. Bucket → hash & (buckets.length - 1). A mask, not a remainder: no division, no negative index.
  • 3. Walk → n.hash == hash && n.key.equals(key). Compare the int first — it is cheaper.
  • 4. Match → change the value and return. Same key means replace, not add.
  • 5. No match → new node at the front of the chain, size++.
  • 6. Then → if (size > buckets.length * 0.75) rehash(); Strictly >, and after the increment.
  • The contract: hashCode picks the bucket, equals confirms the key. Use Objects.hash(…) on exactly the fields equals compares.

The ring buffer: four lines

push(v)    data[tail] = v;  tail = (tail + 1) % data.length;  size++;
poll()     v = data[head];  head = (head + 1) % data.length;  size--;
pop()      tail = (tail - 1 + data.length) % data.length;  v = data[tail];  size--;
element i  data[(head + i) % data.length]     // never data[i]
empty      size == 0        full  size == data.length   // never head == tail
  • The trap: Java's % keeps the sign of the left operand, so (0 - 1) % 8 is -1. Add the length before the modulo.
  • The other trap: after a wrap, slot order and queue order are different lists. Walk the queue, never the array.

Numbers worth remembering

  • Ten adds into a list of four → 12 element copies, 4 then 8.
  • Ten thousand adds, doubling → 16,380 copies. Growing by ten → 49,900 for a thousand.
  • A hundred keys → rehashes at 7, 13, 25, 49, 97; 191 keys moved in total.
  • hashCode() = 1, six keys → 21 comparisons instead of 9. That is 1+2+3+4+5+6.
  • Nine hundred and eighty-five jobs through a sixteen-slot window → ring 0 moves, list 14,775.

📚 All new words from this session
Dynamic array
An array that cannot grow, wrapped in a class that replaces it with a bigger one when it fills. What ArrayList is.
Amortised
The average cost per operation over a long run, when a few operations are much more expensive. add() is O(1) amortised because the growths get rarer.
Capacity
How much room the backing array has. Always at least size, usually more, and never a promise about the future.
Load factor
The fraction of buckets allowed to be occupied before the table doubles. 0.75 in our map and in the JDK's.
Rehash
Building a bigger bucket array and moving every key into the bucket it now belongs to. The index changes because the mask changed, not the hash.
Bucket
One slot of a hash table's array. Holds the head of a chain, or nothing.
Collision
Two different keys wanting the same bucket. Normal, not a bug — a chain is how it is handled.
Chain
The short list of nodes sharing one bucket. A lookup walks it comparing keys.
Spread
How evenly a hash function distributes keys across buckets. The whole of a hash map's performance lives here.
Mask
hash & (length - 1). Turns any int into a legal bucket number with no division and no negative index — which is why the bucket count must be a power of two.
Treeified bin
Java 8's fix for a long chain: past eight entries, the chain becomes a balanced tree, so a lookup in it is O(log n) instead of O(n).
Ring buffer
One fixed array with a head and a tail that wrap with a modulo. Nothing is ever shifted. What ArrayDeque is.
Head / tail
The slot the next element comes out of, and the slot the next element goes into.
Deque
“Double-ended queue”: a structure you can take from either end. push+pop makes it a stack; push+poll makes it a queue.
Fail-fast
An iterator that detects the collection changing underneath it and throws ConcurrentModificationException instead of returning a wrong answer. Our structures have no iterators, so they cannot notice.
Boxing
Wrapping a primitive in an object — int into Integer. The reason ArrayList<Integer> uses far more memory than an int[].
Adapter
A class that makes one interface look like another. JdkDeque maps push to addLast and poll to pollFirst.
Contract test
One suite run against two or more implementations, written only against the interface. Green means they agree on everything anybody wrote down.
