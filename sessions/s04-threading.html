Why This Matters

Imagine a JavaFX app with a "Download" button. If the download runs on the same thread that draws the window, the whole window freezes until the download finishes: no scrolling, no clicking, the dreaded "Not Responding". The fix is to run the slow work on another thread. Servers do the same thing at a huge scale: one web server may serve thousands of users at once, each on their own thread.

🎭
Analogy — a restaurant kitchen

A program (a process) is a restaurant kitchen. A thread is one chef working in it.

  • A kitchen with one chef cooks one dish at a time. That's every program you've written so far: the chef is called main.
  • Hire more chefs and several dishes cook at the same time. They share the same kitchen (the same memory, the same fridge).
  • Each chef follows their own recipe (their run() method) at their own pace.
  • A head chef (the scheduler) decides who gets the stove next, and you don't control the exact order.
Part 1 of 7

Part 1 — What Is a Thread? The Thread Class

A thread is a single path of execution through your code: one "worker" following instructions one after another. A process is a running program; it can contain many threads, and they all share the process's memory. In Java, each thread is represented by an object of the class java.lang.Thread. Through that object you can start the thread, name it, check its state, wait for it, or ask it to stop.

Example 1 — you already have a thread: main

package com.aptech.s04;

/**
 * Example 1 — Every Java program already runs in a thread: the "main" thread.
 */
public class E01_MainThread {
    public static void main(String[] args) {
        Thread me = Thread.currentThread();            // "which thread is running THIS line?"

        System.out.println("Name:     " + me.getName());
        System.out.println("Priority: " + me.getPriority() + "  (1 = lowest, 5 = normal, 10 = highest)");
        System.out.println("Daemon?   " + me.isDaemon());
        System.out.println("Alive?    " + me.isAlive());
        System.out.println("State:    " + me.getState());

        me.setName("boss");                            // you may rename a thread
        System.out.println("Renamed:  " + Thread.currentThread().getName());
    }
}

Part 2 — Creating Threads

A thread needs a job: the code it should run. In Java the job always lives in a method called run(). There are three ways to give a thread its job. All three end the same way: you call start(), and Java creates the new thread and calls run() inside it.

Example 2 — Way 1: extend Thread

package com.aptech.s04;

/**
 * Example 2 — Way 1 to create a thread: EXTEND the Thread class and override run().
 */
public class E02_ExtendThread {

    /** A thread that counts to 3. run() holds the job it will do. */
    static class Counter extends Thread {
        Counter(String name) {
            super(name);                               // give the thread a name
        }

        @Override
        public void run() {
            for (int i = 1; i <= 3; i++) {
                System.out.println(getName() + " says " + i);
                try {
                    Thread.sleep(100);                 // pause 100 ms so the threads take turns
                } catch (InterruptedException e) {
                    return;
                }
            }
        }
    }

    public static void main(String[] args) throws InterruptedException {
        Counter a = new Counter("Ada");
        Counter b = new Counter("Ben");

        a.start();                                     // start() = run() in a NEW thread
        b.start();
        System.out.println("main started both threads and carries on");

        a.join();                                      // wait for Ada to finish
        b.join();                                      // wait for Ben to finish
        System.out.println("Both threads finished");

        // The classic mistake: run() instead of start() does NOT create a thread
        Counter c = new Counter("Chi");
        System.out.println("Calling run() directly...");
        c.run();                                       // runs in the MAIN thread, like any method call
        System.out.println("...main had to wait for Chi, because no new thread was created");
    }
}

19Thread.sleep(100) pauses the current thread for 100 ms. It can throw InterruptedException (if someone asks the thread to stop, Part 5), so it must be caught.

33main doesn't wait: it prints immediately while Ada and Ben are still counting.
35–36join() means "main, wait here until this thread has finished".

✦
Key Point: start(), never run() start() = "create a new thread, and run the job there" (returns immediately). run() = "run the job here, in my thread" (no new thread, no concurrency). And a thread can be started only once: a second start() throws IllegalThreadStateException.

Example 3 — Way 2: implement Runnable (and Way 3: a lambda)

Runnable is an interface with just one method, void run(). You write the job as a Runnable and hand it to a new Thread(job). Because Runnable has only one method, you can also write the job as a lambda (Session 1, Part 3).

package com.aptech.s04;

/**
 * Example 3 — Way 2 (preferred): IMPLEMENT Runnable (the job) and hand it to a Thread (the worker).
 * Way 3: the same thing written as a lambda.
 */
public class E03_ImplementRunnable {

    /** The JOB: what should be done. It is not a thread by itself. */
    static class Greeting implements Runnable {
        private final String message;

        Greeting(String message) { this.message = message; }

        @Override
        public void run() {
            System.out.println(Thread.currentThread().getName() + ": " + message);
        }
    }

    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Thread(new Greeting("Good morning!"), "worker-1");   // job + name
        t1.start();
        t1.join();                                     // wait, so the output stays in order

        Runnable job = () -> System.out.println(Thread.currentThread().getName() + ": Hello from a lambda!");
        Thread t2 = new Thread(job, "worker-2");
        t2.start();
        t2.join();

        // One job can be given to several workers
        Greeting shared = new Greeting("same job, different worker");
        Thread t3 = new Thread(shared, "worker-3");
        Thread t4 = new Thread(shared, "worker-4");
        t3.start();
        t3.join();
        t4.start();
        t4.join();

        System.out.println(Thread.currentThread().getName() + ": all done");
    }
}

Part 3 — Thread States: The Life of a Thread

A thread goes through a life cycle, from being created to being finished. At any moment it is in exactly one of six states, and you can ask which with t.getState(). The states are the values of the enum Thread.State.

StateMeaningKitchen analogy
NEWCreated with new, but start() not called yetThe chef is hired but hasn't come to work
RUNNABLERunning, or ready to run as soon as the scheduler gives it a CPU coreCooking, or waiting for a free stove
BLOCKEDWaiting to enter a synchronized block that another thread holds (Session 5)Waiting outside the one-person pantry
WAITINGWaiting with no time limit, e.g. join()Waiting for another chef to finish the sauce
TIMED_WAITINGWaiting for a set time, e.g. sleep(1000), join(500)"Let the dough rest for 10 minutes"
TERMINATEDrun() has finished; it can never run againThe chef has gone home

Example 4 — catching each state in the act

This example creates situations that put threads into each state, then asks getState(). The short sleep(100)s give each thread time to get into position before we look.

package com.aptech.s04;

/**
 * Example 4 — The six thread states, observed one by one with getState().
 * (Generous pauses make each state easy to catch.)
 */
public class E04_ThreadStates {

    private static final Object LOCK = new Object();
    private static volatile boolean keepSpinning = true;

    public static void main(String[] args) throws InterruptedException {
        // 1) NEW: created, but start() not called yet
        Thread spinner = new Thread(() -> {
            while (keepSpinning) { /* busy working */ }
        });
        System.out.println("After new Thread():      " + spinner.getState());

        // 2) RUNNABLE: started and working (or ready to work)
        spinner.start();
        Thread.sleep(100);
        System.out.println("While working:           " + spinner.getState());
        keepSpinning = false;
        spinner.join();

        // 3) TIMED_WAITING: sleeping for a fixed time
        Thread sleeper = new Thread(() -> {
            try { Thread.sleep(1000); } catch (InterruptedException e) { /* woken early */ }
        });
        sleeper.start();
        Thread.sleep(100);
        System.out.println("During sleep(1000):      " + sleeper.getState());
        sleeper.interrupt();                           // wake it up early
        sleeper.join();

        // 4) WAITING: waiting with NO time limit (here: join on a thread that sleeps)
        Thread slow = new Thread(() -> {
            try { Thread.sleep(500); } catch (InterruptedException e) { /* ignore */ }
        });
        Thread waiter = new Thread(() -> {
            try { slow.join(); } catch (InterruptedException e) { /* ignore */ }
        });
        slow.start();
        waiter.start();
        Thread.sleep(100);
        System.out.println("During join() (no limit): " + waiter.getState());
        waiter.join();

        // 5) BLOCKED: waiting to enter a synchronized block that another thread holds
        Thread blocked = new Thread(() -> {
            synchronized (LOCK) { /* can only get in when main lets go */ }
        });
        synchronized (LOCK) {                          // main holds the lock...
            blocked.start();
            Thread.sleep(100);
            System.out.println("Waiting for a lock:      " + blocked.getState());
        }                                              // ...and lets go here
        blocked.join();

        // 6) TERMINATED: run() has finished
        System.out.println("After run() ends:        " + blocked.getState());
    }
}
LineWhat it does, in plain English
9–10A lock object for part 5, and a flag the spinner checks. volatile makes sure the spinner sees when main changes it (more on this in Session 5).
14–17Created, not started: NEW.
20–22Started and busy looping: RUNNABLE. Then we stop the loop and join.
27–32A thread inside sleep(1000): TIMED_WAITING. We wake it early with interrupt().
37–46waiter calls slow.join(), waiting with no time limit: WAITING.
50–57main enters synchronized (LOCK) first, so blocked can't get in and waits at the door: BLOCKED. When main leaves the block, the other thread gets in.
61After its job ends: TERMINATED.
After new Thread(): NEW While working: RUNNABLE During sleep(1000): TIMED_WAITING During join() (no limit): WAITING Waiting for a lock: BLOCKED After run() ends: TERMINATED
ℹ️
"Running" is not a Java state Many books draw separate "Ready" and "Running" states. Java combines them into one: RUNNABLE means "running or ready to run". Whether it's on a CPU core at this exact microsecond is up to the operating system.

package com.aptech.s04;

/**
 * Example 5 — The most-used Thread methods: start, sleep, join, isAlive, getName/setName, priority.
 */
public class E05_ThreadMethods {
    public static void main(String[] args) throws InterruptedException {
        Thread download = new Thread(() -> {
            for (int percent = 25; percent <= 100; percent += 25) {
                try {
                    Thread.sleep(150);                  // pretend to download a piece
                } catch (InterruptedException e) {
                    return;
                }
                System.out.println("  " + Thread.currentThread().getName() + " " + percent + "%");
            }
        });

        download.setName("downloader");
        download.setPriority(Thread.MAX_PRIORITY);      // a HINT to the scheduler (10), not a guarantee
        System.out.println("Name: " + download.getName() + ", priority: " + download.getPriority());
        System.out.println("Alive before start()? " + download.isAlive());

        download.start();
        System.out.println("Alive after start()?  " + download.isAlive());

        download.join();                                // main waits here until the download is done
        System.out.println("Alive after join()?   " + download.isAlive());

        // join(ms) waits at most that long
        Thread slow = new Thread(() -> {
            try { Thread.sleep(2000); } catch (InterruptedException e) { /* stopped */ }
        });
        slow.start();
        slow.join(300);                                 // give up waiting after 300 ms
        System.out.println("Still running after join(300)? " + slow.isAlive());
        slow.interrupt();                               // tidy up: ask it to stop
        slow.join();
    }
}

Part 5 — Managing Threads: Waiting and Stopping

Managing threads mostly means two things: waiting for them to finish (join(), which you've seen), and stopping them when their work is no longer needed, for example when the user presses "Cancel". Java has no safe way to force a thread to stop. The old Thread.stop() could leave data half-changed, so it was deprecated for decades and in modern Java it simply throws UnsupportedOperationException. Instead, you ask politely with interrupt(), and the thread cooperates.

🎭
Analogy — tapping a chef on the shoulder You can't yank a chef out of the kitchen mid-recipe, because the pot might boil over. You tap them on the shoulder ("please stop") and they turn off the stove, clean up, and leave. interrupt() is the tap. The thread notices it in two ways: sleep()/join() throw InterruptedException, or the loop checks isInterrupted(). 
package com.aptech.s04;

/**
 * Example 6 — Managing threads: how to STOP a thread politely with interrupt().
 * (Java has no safe "kill" button — the thread must agree to stop.)
 */
public class E06_StoppingThreads {
    public static void main(String[] args) throws InterruptedException {
        Thread clock = new Thread(() -> {
            int tick = 0;
            while (!Thread.currentThread().isInterrupted()) {   // keep going until asked to stop
                tick++;
                System.out.println("tick " + tick);
                try {
                    Thread.sleep(200);
                } catch (InterruptedException e) {
                    System.out.println("interrupted while sleeping - cleaning up");
                    return;                                      // leave run(), so the thread ends
                }
            }
        }, "clock");

        clock.start();
        Thread.sleep(500);                  // let it tick for about half a second
        System.out.println("main: please stop, clock");
        clock.interrupt();                  // politely ask the thread to stop
        clock.join();
        System.out.println("clock state: " + clock.getState());
    }
}
LineWhat it does, in plain English
11The loop keeps going only while nobody has asked it to stop. This is the check for threads that are busy (not sleeping) when the tap comes.
15Most of its time is spent sleeping…
16–18…so the tap usually arrives during sleep, which throws InterruptedException. We clean up and return, which ends run() and so the thread.
24main lets the clock tick for about half a second (ticks at 0, 200 and 400 ms).
26–27Ask it to stop, then wait until it really has.
tick 1 tick 2 main: please stop, clock interrupted while sleeping - cleaning up clock state: TERMINATED
⚠️
Never swallow an interrupt 
try { Thread.sleep(200); } catch (InterruptedException e) { }   // BAD: the "please stop" is lost
An empty catch throws the request away, and your thread may never stop. Either leave run() (as above), or restore the flag with Thread.currentThread().interrupt(); so code further up can see it (Example 8 does this).
✦
Key Point Wait with join(). Stop with interrupt(), and write your run() so it reacts: return from catch (InterruptedException e) and check isInterrupted() in loops. Never use stop().

Part 6 — Daemon Threads

Java keeps your program running as long as at least one normal ("user") thread is alive. A daemon thread is a background helper that does not count: when the last user thread finishes, the JVM exits and switches all daemon threads off, even in the middle of their work. Use daemons for background chores that should never keep the program open: autosave, a clock, a status reporter. Java's own garbage collector runs on daemon threads. 

package com.aptech.s04;

/**
 * Example 7 — Daemon threads: background helpers that do NOT keep the program alive.
 */
public class E07_DaemonThreads {
    public static void main(String[] args) throws InterruptedException {
        Thread autosave = new Thread(() -> {
            int n = 0;
            while (true) {                              // runs "forever"...
                n++;
                System.out.println("  [autosave #" + n + "]");
                try {
                    Thread.sleep(300);
                } catch (InterruptedException e) {
                    return;
                }
            }
        }, "autosave");

        autosave.setDaemon(true);                       // MUST be called before start()
        autosave.start();
        System.out.println("autosave is a daemon? " + autosave.isDaemon());

        System.out.println("main: typing a document...");
        Thread.sleep(1000);
        System.out.println("main: finished - the program ends now.");
        // No join and no interrupt: when the last NON-daemon thread (main) ends,
        // the JVM stops and daemon threads are simply switched off.
    }
}
LineWhat it does, in plain English
10while (true): this job never ends by itself.
21setDaemon(true) makes it a background thread. It must be called before start(), or you get IllegalThreadStateException.
25–27main works for 1 second (the autosave ticks about 4 times: at 0, 300, 600 and 900 ms), then main ends…
28–29…and because the only thread left is a daemon, the program ends too. Remove line 21 and the program would run forever.

Real output of one run (the first autosave line may come before or after "main: typing"):

autosave is a daemon? true main: typing a document... [autosave #1] [autosave #2] [autosave #3] [autosave #4] main: finished - the program ends now.

Part 7 — Virtual Threads, and Converting to Them with AI Help

Platform threads vs virtual threads

Every thread you've made so far is a platform thread: a thin wrapper around a real operating-system thread. OS threads are expensive: each reserves memory for its stack, and a computer can only handle a few thousand at once. That's a problem for programs that do thousands of things that mostly wait (for a website, a database, a file).

Virtual threads (standard since Java 21) are threads managed by Java itself. They're so cheap you can create millions. Behind the scenes, Java runs them on a small number of platform "carrier" threads, and whenever a virtual thread starts waiting, Java parks it and uses the carrier for another virtual thread.

🎭
Analogy — waiters and orders With platform threads, every customer order gets its own waiter, who stands at the kitchen door doing nothing while the food cooks. 100 waiters = at most 100 orders. With virtual threads, orders are slips of paper (cheap!). A handful of waiters carry whichever slip is ready and never stand around waiting. Thousands of orders, the same few waiters.

Example 8 — 10,000 waiting tasks

package com.aptech.s04;

import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

/**
 * Example 8 — Virtual threads (Java 21+): cheap, lightweight threads for work that WAITS a lot.
 */
public class E08_VirtualThreads {

    /** A task that mostly waits, like calling a web service or a database. */
    static void callSlowService() {
        try {
            Thread.sleep(1000);                         // 1 second of waiting
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }

    public static void main(String[] args) throws InterruptedException {
        // 1) Creating ONE virtual thread
        Thread v = Thread.ofVirtual().name("virtual-1").start(
                () -> System.out.println("Hello from " + Thread.currentThread().getName()
                        + " (virtual? " + Thread.currentThread().isVirtual() + ")"));
        v.join();

        // 2) 10,000 tasks, each waiting 1 second, all at the same time
        long start = System.currentTimeMillis();
        List<Thread> threads = new ArrayList<>();
        for (int i = 0; i < 10_000; i++) {
            threads.add(Thread.ofVirtual().start(E08_VirtualThreads::callSlowService));
        }
        for (Thread t : threads) {
            t.join();
        }
        System.out.println("10,000 virtual threads finished in about "
                + Math.round((System.currentTimeMillis() - start) / 1000.0) + " second(s)");

        // 3) The same with an ExecutorService (the style you will use most often)
        start = System.currentTimeMillis();
        try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i < 10_000; i++) {
                executor.submit(E08_VirtualThreads::callSlowService);
            }
        }                                               // close() waits for every task to finish
        System.out.println("Executor with virtual threads: about "
                + Math.round((System.currentTimeMillis() - start) / 1000.0) + " second(s)");

        // 4) For comparison: a pool of 100 ordinary (platform) threads needs 100 rounds
        start = System.currentTimeMillis();
        try (ExecutorService pool = Executors.newFixedThreadPool(100)) {
            for (int i = 0; i < 1_000; i++) {           // only 1,000 tasks, otherwise we'd wait 100 s!
                pool.submit(E08_VirtualThreads::callSlowService);
            }
        }
        System.out.println("1,000 tasks on 100 platform threads: about "
                + Math.round((System.currentTimeMillis() - start) / 1000.0) + " second(s)");
    }
}
LineWhat it does, in plain English
14–20A task that just waits 1 second, like a slow network call. Line 18 restores the interrupt flag instead of swallowing it (Part 5).
24–27Thread.ofVirtual().name(…).start(job) creates and starts one virtual thread. isVirtual() confirms it.
31–3710,000 virtual threads, each waiting 1 second, all at once. Try that with platform threads and many computers would run out of memory.
43–47The everyday style: an ExecutorService that gives each task its own virtual thread. In try-with-resources, close() waits for all tasks.
53–57For comparison, a pool of 100 platform threads can only wait for 100 tasks at a time: 1,000 tasks need 10 rounds of 1 second.

⚠️
Virtual threads are not magic speed They help when tasks wait. A task that calculates non-stop (like Practice 3's sum) keeps a CPU core busy either way; for that, the number of cores is the limit.

Converting old code with an AI assistant

Lots of existing Java code uses pools of platform threads. Converting it to virtual threads is a job AI coding assistants (Windsurf, which you'll install in Session 10, GitHub Copilot, ChatGPT, Claude…) are good at, as long as you give a clear request and check the answer. Here's the process, step by step.

🤖 The 4-step AI conversion routine
1
Pick code that waits. Example 9a checks 200 web addresses (each call waits 200 ms) with a fixed pool of 20 platform threads. That's a perfect candidate.
2
Write a precise prompt. Say what you want, what must not change, and ask for explanations. For example:
Convert this Java 25 code from a fixed thread pool of platform threads to virtual threads. Keep the behaviour and the output exactly the same. Use try-with-resources for the ExecutorService. Mark every line you change with a // CHANGED comment and explain each change. Tell me if anything in this code could be a problem with virtual threads (synchronized blocks, ThreadLocal, CPU-heavy work, native calls).
3
Review the answer with the checklist below, never paste it blindly.
4
Run both versions and compare: same results? faster? Then commit.

Before (the legacy code):

        long start = System.currentTimeMillis();
        ExecutorService pool = Executors.newFixedThreadPool(20);     // only 20 workers
        try {
            List<Future<String>> results = new ArrayList<>();
            for (String url : urls) {
                results.add(pool.submit(() -> check(url)));
            }
            int ok = 0;
            for (Future<String> f : results) {
                if (f.get().endsWith("OK")) ok++;
            }
            System.out.println(ok + " sites checked with 20 platform threads in about "
                    + (System.currentTimeMillis() - start) / 100 * 100 + " ms");
        } finally {
            pool.shutdown();
        }

After (the AI's suggestion, after our review):

        long start = System.currentTimeMillis();
        // CHANGED: one cheap virtual thread per task, instead of a fixed pool of 20 platform threads.
        // CHANGED: try-with-resources - close() waits for all tasks, so no finally/shutdown is needed.
        try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
            List<Future<String>> results = new ArrayList<>();
            for (String url : urls) {
                results.add(executor.submit(() -> check(url)));
            }
            int ok = 0;
            for (Future<String> f : results) {
                if (f.get().endsWith("OK")) ok++;
            }
            System.out.println(ok + " sites checked with virtual threads in about "
                    + (System.currentTimeMillis() - start) / 100 * 100 + " ms");
        }

Real output of both (timings vary):

200 sites checked with 20 platform threads in about 2000 ms
200 sites checked with virtual threads in about 200 ms

Only one real line changed (newFixedThreadPool(20) → newVirtualThreadPerTaskExecutor(), plus try-with-resources instead of finally { shutdown(); }), and 200 waits of 200 ms now overlap completely.

✅
Checklist: reviewing an AI's virtual-thread conversion
  1. Does the work actually wait? If it's pure calculation, virtual threads won't help. Reject the change.
  2. No pools of virtual threads. Virtual threads are cheap, so each task should get a new one (newVirtualThreadPerTaskExecutor()). If the AI wraps them in a fixed-size pool, that's wrong.
  3. Limits moved? The old pool of 20 also acted as a limit (at most 20 calls to a server at once). If that limit mattered, you need another way to keep it (a Semaphore, Session 5).
  4. ThreadLocal used as a cache? With millions of virtual threads, a per-thread cache can use a lot of memory. Ask the AI to point these out.
  5. Pinning. Before Java 24, a virtual thread waiting inside a synchronized block "pinned" (blocked) its carrier. Since JDK 24 (JEP 491) that's fixed; native code can still pin. On Java 21–23, prefer ReentrantLock around waits.
  6. Behaviour unchanged? Same output, same exceptions handled, resources still closed. Run it!
  7. Understand every line before you keep it. If you can't explain a line, ask the AI to explain it, or don't use it.
✦
Key Point Virtual threads (Thread.ofVirtual().start(job), Executors.newVirtualThreadPerTaskExecutor()) make thousands of waiting tasks cheap. An AI assistant can do the conversion quickly, but you give it a precise prompt, review its answer with the checklist, and test before you trust it.

🛠 Guided Lab: The Busy Kitchen

Three chefs cook three dishes at the same time, a waiter waits for all of them, and a background clock announces the time. You'll use Runnable, start, sleep, join and a daemon thread together. Pair up; swap the typist after step 3.

📝 Lab checklist (about 30 minutes)
1
The job. Inside a class Kitchen, write static class Chef implements Runnable with fields dish, steps and msPerStep and a constructor.

👀 Show the complete lab solution (try on your own first!) 
package com.aptech.s04.lab;

import java.util.ArrayList;
import java.util.List;

/**
 * GUIDED LAB — The Busy Kitchen: several chefs cook at the same time, the waiter waits for all of them,
 * and a background clock (daemon) announces the time.
 */
public class Kitchen {

    /** STEP 1 — the JOB of one chef: prepare a dish in a number of steps. */
    static class Chef implements Runnable {
        private final String dish;
        private final int steps;
        private final int msPerStep;

        Chef(String dish, int steps, int msPerStep) {
            this.dish = dish;
            this.steps = steps;
            this.msPerStep = msPerStep;
        }

        @Override
        public void run() {
            String me = Thread.currentThread().getName();
            for (int i = 1; i <= steps; i++) {
                try {
                    Thread.sleep(msPerStep);                  // STEP 2 — cooking takes time
                } catch (InterruptedException e) {
                    System.out.println(me + " was stopped!");
                    return;
                }
                System.out.println("  " + me + ": " + dish + " step " + i + "/" + steps);
            }
            System.out.println("  " + me + ": " + dish + " is READY");
        }
    }

    public static void main(String[] args) throws InterruptedException {
        // STEP 5 — a daemon clock that announces the time every 250 ms
        Thread clock = new Thread(() -> {
            int ms = 0;
            while (true) {
                try {
                    Thread.sleep(250);
                } catch (InterruptedException e) {
                    return;
                }
                ms += 250;
                System.out.println("[clock] " + ms + " ms");
            }
        }, "clock");
        clock.setDaemon(true);
        clock.start();

        // STEP 3 — three chefs, three threads, working at the same time
        List<Thread> chefs = new ArrayList<>();
        chefs.add(new Thread(new Chef("Jollof rice", 3, 300), "Chef Ada"));
        chefs.add(new Thread(new Chef("Pepper soup", 2, 400), "Chef Ben"));
        chefs.add(new Thread(new Chef("Puff-puff", 4, 150), "Chef Chi"));

        long start = System.currentTimeMillis();
        for (Thread chef : chefs) {
            chef.start();
        }

        // STEP 4 — the waiter waits until EVERY chef has finished
        for (Thread chef : chefs) {
            chef.join();
        }
        long took = System.currentTimeMillis() - start;
        System.out.println("Waiter: all dishes ready - dinner is served! (about " + (took / 100 * 100) + " ms)");
        System.out.println("Cooking one after another would take about " + (3 * 300 + 2 * 400 + 4 * 150) + " ms");
    }
}

⚠️ Common Mistakes (and the Exact Error You'll See)

Every message below was produced on JDK 25.

🚫
Mistake 1 — calling run() instead of start()

No error, which is what makes it dangerous: the code runs, but on the current thread, one job after another. Example 2 (Chi) and Lab experiment (c) show it. Fix: start().

🚫
Mistake 2 — starting the same thread twice 
Thread t = new Thread(job);
t.start();
t.start();
Exception in thread "main" java.lang.IllegalThreadStateException at java.base/java.lang.Thread.start(Thread.java:1416)

Fix: a Thread object is single-use. To run the job again, create a new Thread(job).

🚫
Mistake 3 — setDaemon(true) after start() 
t.start();
t.setDaemon(true);
Exception in thread "main" java.lang.IllegalThreadStateException at java.base/java.lang.Thread.setDaemon(Thread.java:2044)

Fix: swap the two lines. You decide what kind of thread it is before it starts.

🚫
Mistake 4 — not handling InterruptedException (compile error) 
void m() { Thread.sleep(100); }
error: unreported exception InterruptedException; must be caught or declared to be thrown

Fix: wrap it in try { … } catch (InterruptedException e) { return; } inside run(), or add throws InterruptedException to methods like main. (Note: run() itself can't declare throws, so you must catch there.)

🚫
Mistake 5 — changing a local variable inside a lambda 
int count = 0;
Thread t = new Thread(() -> count++);
error: local variables referenced from a lambda expression must be final or effectively final

Why: the lambda may run later, on another thread, after the method has finished, so Java only lets it read local variables that never change. Fix: give each thread its own slot in an array or object (like partial[part] in Practice 3). Safely sharing a counter between threads is Session 5.

🚫
Mistake 6 — reading a thread's result without join() 
t.start();                                   // t computes a big sum into result[0]
System.out.println(result[0]);               // too early!
Result without join(): 0 Result after join(): 1250000025000000

Fix: t.join() before using anything the thread produced. join() also guarantees you see the thread's latest values.

🚫
Mistake 7 — trying to kill a thread with stop() 
t.stop();
Exception in thread "main" java.lang.UnsupportedOperationException at java.base/java.lang.Thread.stop(Thread.java:1557)

Fix: t.interrupt(), and make the thread react to it (Part 5).

🚫
Mistake 8 — a program that never ends

No error; the program just keeps running after main finishes. Why: a non-daemon thread is still alive (often a while (true) loop, or an ExecutorService that was never shut down). Fix: make background helpers daemons, stop workers with interrupt(), and close executors (try-with-resources).

Medium  P3 — Parallel sum

Add up 1 to 1,000,000 using 4 threads, each summing one quarter. Combine the four results and compare with the formula n(n+1)/2.

💡 Hint

Give each thread its own slot in a long[] partial so no two threads ever change the same variable. Copy the loop variable into a final int part for the lambda (Mistake 5). Join before reading.

✅ Solution
package com.aptech.s04.practice;

/** Practice 3 (medium) — add up 1..1,000,000 with 4 threads; each thread sums its own quarter. */
public class P3_ParallelSum {
    public static void main(String[] args) throws InterruptedException {
        int n = 1_000_000;
        int parts = 4;
        long[] partial = new long[parts];              // each thread writes ONLY its own slot
        Thread[] workers = new Thread[parts];

        for (int p = 0; p < parts; p++) {
            final int part = p;                        // lambdas need a final (unchanging) variable
            int from = part * (n / parts) + 1;
            int to = (part + 1) * (n / parts);
            workers[p] = new Thread(() -> {
                long sum = 0;
                for (int i = from; i <= to; i++) {
                    sum += i;
                }
                partial[part] = sum;
            }, "adder-" + p);
            workers[p].start();
        }

        long total = 0;
        for (int p = 0; p < parts; p++) {
            workers[p].join();                         // wait, THEN read that thread's result
            System.out.println(workers[p].getName() + " -> " + partial[p]);
            total += partial[p];
        }
        System.out.println("Total:    " + total);
        System.out.println("Formula:  " + (long) n * (n + 1) / 2);
    }
}

package com.aptech.s04.practice;

/** Practice 5 (challenge) — a relay race: each runner's thread join()s the previous runner before starting. */
public class P5_RelayRace {

                if (previous != null) {

Challenge  P6 — 1,000 prices with virtual threads

Each "price lookup" waits 300 ms. Fetch 1,000 prices with a virtual-thread executor, storing each result in its own array slot, then total them and report the time.

💡 Hint

Executors.newVirtualThreadPerTaskExecutor() in try-with-resources. Submitting a lambda that returns a value makes it a Callable, which is allowed to throw InterruptedException.

✅ Solution
package com.aptech.s04.practice;

import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

/** Practice 6 (challenge) — "fetch" 1,000 prices with virtual threads, each result in its own array slot. */
public class P6_PriceFetcher {

    /** Pretend network call: waits 300 ms, then returns a price based on the product number. */
    static int fetchPrice(int productId) throws InterruptedException {
        Thread.sleep(300);
        return 100 + productId % 50;
    }

    public static void main(String[] args) {
        int count = 1_000;
        int[] prices = new int[count];

        long start = System.currentTimeMillis();
        try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int id = 0; id < count; id++) {
                final int product = id;
                executor.submit(() -> {
                    prices[product] = fetchPrice(product);   // each task writes only its own slot
                    return null;                              // return makes this a Callable, which may throw
                });
            }
        }                                                     // waits for all 1,000 tasks
        long ms = (System.currentTimeMillis() - start) / 100 * 100;       // rounded down to 100 ms

        long total = 0;
        for (int p : prices) {
            total += p;
        }
        System.out.println("Fetched " + count + " prices, total N" + total);
        System.out.println("Took about " + ms + " ms (one after another it would take about " + count * 300 / 1000 + " s)");
    }
}

📋 Cheat Sheet

Create & start

Thread t = new Thread(() -> doWork(), "worker");
t.start();                       // never t.run()
class Job implements Runnable { public void run() { ... } }
new Thread(new Job()).start();

Wait

t.join();          // wait until t ends
t.join(500);       // wait at most 500 ms
t.isAlive();

Pause

try {
    Thread.sleep(200);             // current thread
} catch (InterruptedException e) {
    return;                        // or: Thread.currentThread().interrupt();
}

Stop politely

t.interrupt();                               // caller
while (!Thread.currentThread().isInterrupted()) { ... }   // worker

Info

Thread.currentThread().getName();
t.setName("x"); t.setPriority(Thread.MAX_PRIORITY);
t.getState();   // NEW RUNNABLE BLOCKED WAITING TIMED_WAITING TERMINATED

Daemon

t.setDaemon(true);   // BEFORE start()
t.start();

Virtual threads (Java 21+)

Thread v = Thread.ofVirtual().name("v1").start(job);
try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {
    ex.submit(job);
}   // close() waits for all tasks

🎓 Session Summary

  1. A thread is one path of execution; a process can run many at once, sharing memory. Thread objects represent them.
  2. Create threads with a Runnable/lambda (preferred) or by extending Thread; always call start(), only once.
  3. Six states: NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, TERMINATED (getState()).
  4. Key methods: sleep, join, isAlive, names, priorities (hints only), interrupt.
  5. Manage threads by joining them and interrupting them politely. There's no safe forced stop.
  6. Daemon threads don't keep the program alive; set them before start().
  7. Virtual threads make thousands of waiting tasks cheap. AI can convert old code, but you prompt precisely, review with a checklist, and test.
  8. The order in which threads run is not guaranteed. Correct programs must not depend on it.
📚 All new words from this session
Thread, process, main thread
A path of execution / a running program / the thread that runs main.
Concurrency, scheduler
Several things in progress at once / the OS part that decides which thread runs.
Runnable
An interface with one method, run(): a job a thread can do.
start() / run()
Begin a new thread that runs the job / the job itself.
Thread states
NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, TERMINATED.
join, sleep, interrupt
Wait for another thread / pause this one / politely ask a thread to stop.
Priority
A 1–10 hint to the scheduler, never a guarantee.
Daemon thread / user thread
A background thread that doesn't keep the JVM alive / one that does.
Platform thread / virtual thread / carrier thread
A wrapper around an OS thread / a cheap thread managed by Java / the platform thread a virtual thread runs on.
ExecutorService
An object that runs submitted tasks on threads for you (more in Session 5).
Pinning
When a virtual thread can't release its carrier while waiting (mostly fixed since JDK 24).
