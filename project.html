One application, built by you, from an empty project to a working desktop program with a real database behind it. Everything the eighteen sessions teach — collections, generics, files, threads, JDBC, transactions, design patterns, tests — arrives in one place. On this page

What You Are Building

A JavaFX desktop application with a database behind it. The running example through the whole course is the Student Registry — the same registry you built as a class in Session 1, moved onto a file in Session 3, and put on an embedded H2 database in Session 7. The capstone is that program with a proper window in front of it.

✦
The one rule: it must be yours

You may choose a different subject if your teacher approves it — a library system, an inventory tracker, a booking tool. What you may not do is hand in a tutorial you followed. Every milestone is reviewed against your own repository history, and the viva asks you to change something live. Pick a subject you can talk about for ten minutes without notes.

What "done" looks like

  • A window that opens and does something useful, not a blank Stage
  • Data that survives being closed — an embedded H2 database, not a list that empties on exit
  • Writes that cannot half-happen — transactions around anything that touches two tables
  • A test suite that would catch a regression, and that you can run in front of someone
  • Clean layering — the UI does not contain SQL, and the database code does not contain Label
  • You can defend every line in the viva

The Four Milestones

Each milestone is a checkpoint where you show working software, not a document. They are paced to land just after the session that gives you the skill, so you are never asked to use something you have not been taught.

🔹 Milestone 1 · The Shell — a window that looks like the finished product

After: Session 15 (coming soon) (Layouts, CSS, Controls & Charts) and Session 16 (coming soon) (Event Handling).  Weight: 10% of the capstone.

What you hand in

  • A JavaFX application that opens a window with your real layout — a BorderPane shell, a table or list of your records, and at least one chart
  • Styling in a CSS file, not inline setStyle() calls scattered through the code
  • The buttons and menu present and wired to something, even if that something is a placeholder

Marked on

Does it run? Does it look deliberate rather than default? Is the layout built with layout panes rather than absolute positioning? Is the CSS in one place you can point at?

Common way to lose marks: an application that only works at one window size, because everything was positioned with setLayoutX().

🔹 Milestone 2 · The Data Layer — it remembers

After: Session 8 (Advanced JDBC), which is also when A4 is under way.  Weight: 10% of the capstone.

What you hand in

  • An embedded H2 database — the schema created on first run with IF NOT EXISTS, so it is safe to start twice
  • A DAO (or repository) with every value passed through ? — no string concatenation in SQL, anywhere
  • Transactions around any operation that writes to more than one table, with rollback in the failure path
  • Seed data, so the app is not empty the first time it opens

Marked on

Most of this is A4, reused. The question that separates the bands: can you show me a test that breaks the second write and proves the first one never happened?

Common way to lose marks: a catch block that rolls back and then returns normally — so the caller is told the save worked when it did not.

🔹 Milestone 3 · Real Behaviour — it does the job

After: Session 9 (coming soon) (Design Patterns) and Session 10 (coming soon) (Unit Testing & AI Tools).  Weight: 10% of the capstone.

What you hand in

  • Full create / read / update / delete through the UI — add a record, edit it, search for it, delete it
  • Validation with feedback: a bad amount or a blank name produces a message, not a stack trace on the console
  • A JUnit test suite covering the logic that is not the UI — the DAO and the business rules
  • Long operations do not freeze the window — they run off the UI thread (the lesson from Sessions 4–5)

Marked on

Do the tests actually assert behaviour, or do they just call the method and pass? Can you make a small change and watch a test go red?

Common way to lose marks: a test suite where every test would still pass if you deleted the method body.

🔹 Milestone 4 · Demo & Viva — you own it

In: Week 5 (coming soon).  Weight: 70% of the capstone, and the only part you cannot do the night before.

What happens

  • A short live demo — the application running, doing the thing it is for
  • A viva: your teacher opens your code and asks you to explain, and to change, a specific part
  • Submitted work: your repository, a README that says how to run it, and your test suite

Marked on

The four dimensions used all course — Correctness, Design, Style, Documentation & Tests — plus the viva, which is where a project that was clearly written by somebody else falls apart. Expect questions like "what happens if I delete this line?", "why a PreparedStatement here and not there?" and "where is the transaction boundary, and why is it there?"

⚠️
The three ways capstones actually fail
  1. Leaving the database until last. It is the deepest part and the one that cannot be rushed. Milestone 2 exists so this cannot happen to you.
  2. No tests until the end. A test written after the code proves nothing. Write the test at Milestone 3 and keep it green.
  3. Code you cannot explain. If an AI wrote it and you accepted it without understanding, the viva will find it. That is the whole reason the viva exists.
