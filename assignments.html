How Each Assignment Works

Every assignment follows the same pattern, so once you have done A1 you know how to approach all of them. You are never asked to write a program from a blank file.

StepWhat happens
1. Open the starterIn IntelliJ, File → Open the code/aN-…-starter folder. You get a complete project with a pom.xml.
2. Run SelfCheck firstIt will report something like 0 passed, 12 failed. That is expected. You are not behind — you are at the start.
3. Do the TODOs, one at a timeEach one has a hint. After each, re-run SelfCheck and watch a FAIL turn into a PASS. This is the whole loop.
4. Target: all PASSWhen SelfCheck reports every check passing, run the Main program and try it yourself.
5. Hand inCommit your work to your repository. Your teacher may also ask for a short demo or a viva question.

The rubric — every assignment, the same four dimensions
Correctness (work it, prove it) Does it do what the brief asks? SelfCheck all green, from a clean build, repeatedly.
Design (the right shape) Is the right collection, the right concurrency tool, the right transaction boundary used — and could you defend the choice?
Style (a human reads this) Clear names, consistent formatting, no dead code, no leftover System.out.println debugging.
Documentation & tests Comments that give the reason, not the obvious; Javadoc on public methods; tests that would catch a regression.

The Six Assignments

Each assignment builds on the one before it. A1 and A2 are separate programs; from A3 onwards you are extending the same Student Registry you have been carrying since Session 1, until it becomes the core of your capstone.

📋 A1 · Student Registry · worth 10% of your course grade

Issued: Session 1. Due: before the start of Session 3 (your teacher will confirm the date).  Time needed: about 3–4 hours.  Work: individual.

🎯 The brief

Aptech's front desk needs a small program to register students, find them, count them per course and manage a waiting list for the computer lab. The menu and screen output are already written — your job is the engine behind it, the class StudentRegistry, using the right collection for each task.

📦 What you get

  • code/a1-student-registry-starter — open this folder in IntelliJ
  • Student.java and Main.java — complete, do not change
  • SelfCheck.java — the automatic checker, do not change. Target: 12 passed
  • StudentRegistry.java — the file you complete; every method has a // TODO and a hint

Practises: every part of Session 1 — List, Set, Map, Queue, sorting and searching.

📋 A2 · Student Record File Manager · worth 10% of your course grade

Issued: Session 3. Due: before the start of Session 5 (your teacher will confirm).  Time needed: about 3–4 hours.  Work: individual.

🎯 The brief

The registry from A1 now has to survive being switched off. Read student records from a file, clean them up, write them back, and prove the whole round trip loses nothing — using Path, Files, buffered readers and writers, and the Stream API.

📦 What you get

  • code/a2-student-file-manager-starter
  • A sample data file with deliberately messy rows for you to parse and normalise
  • SelfCheck — all checks must pass

Practises: every part of Session 3 — streams, buffering, charsets, and why a try-with-resources is not optional.

📋 A3 · Concurrent File Processor · worth 10% of your course grade

Issued: Session 5. Due: before the start of Session 6 (your teacher will confirm).  Time needed: about 3–4 hours.  Work: individual.

🎯 The brief

Process many files at once, without losing a single one and without corrupting a shared total. This is the assignment where the two classic concurrency bugs stop being theory: you will meet a race condition, and you will be expected to explain which line caused it.

📦 What you get

  • code/a3-concurrent-file-processor-starter
  • Reuses the DownloadManager shape from lab task L4
  • SelfCheck — all checks must pass, and must keep passing when run repeatedly

Practises: executors, thread pools, Future, and the atomicity discipline Sessions 4–5 drilled.

📋 A4 · Student Registry on H2 · worth 10% of your course grade

Issued: Session 7. Extended in: Session 8. Due: before the start of Session 12 (coming soon) (your teacher will confirm).  Time needed: about 4–5 hours.  Work: individual.

🎯 The brief — two halves, one project

Take the Student Registry you have carried since Session 1 and give it a real database: an embedded H2 file, reached through JDBC, behind a DAO. This assignment is issued in Session 7 and extended in Session 8 rather than replaced — keep your code, you build on it.

Part 1 — the DAO (Session 7)

  1. createSchema() — two tables, safe to call twice (IF NOT EXISTS)
  2. insert(…) — add a student and return the database-generated id
  3. findById(id) — one student, or null when there is none
  4. searchByName(text) — a parameterized LIKE search. SelfCheck fires an SQL injection at it; it must return nothing
  5. updateMark and delete — each returns the number of rows changed
  6. count() and columnNames() — the latter read from DatabaseMetaData, not hard-coded

Part 2 — transactions (Session 8)

  1. Two tables: enrolments(student_id, course_id, paid) and fee_payments(enrolment_id, amount, paid_at), with foreign keys to what they reference
  2. enrolAndPay(studentId, courseId, fee) — three writes, one transaction. If any part fails, nothing is left behind
  3. postPayments(enrolmentId, amounts[]) — a savepoint per payment, so one bad amount does not lose the good ones
  4. reconcile() — total paid against the course fee for every enrolment, with a state of settled, part-paid or unpaid
Correctness SelfCheck reports all PASS, from a clean build, every run.
Safety Every value goes through a ?. The injection check passes because there is no concatenation anywhere.
Atomicity Break the second write on purpose in a test and prove the first one is absent afterwards. A reviewer should be able to run that test.
Resources Every Connection, Statement and ResultSet closed with try-with-resources; no connection held in a field.

📦 What you get

  • code/a4-student-registry-jdbc-starter — including lib/h2-2.3.232.jar, so it compiles and runs offline with no download
  • Worked reference: code/s08-advanced-jdbc — the same techniques, fully commented
  • The H2 & MySQL guide for anything the sessions did not cover
📋 A5 · A Patterned Registry · worth 10% of your course grade

Issued: Session 9. Second half issued: Session 10 — Unit Testing & AI Tools. Due: before the start of Session 11 (coming soon).  Time needed: about 5–6 hours across the two weeks.  Work: individual.

🎯 The brief — restructure the registry, then prove it

Take the transactional registry from A4 and change its shape without changing what it does. Today it works; after A5 it is arranged so that the next person can change it. The behaviour you built in A4 stays — same tables, same data, same answers — but the database moves behind an interface, and nothing above that interface may know it is there.

Part 1 — the refactor (Session 9)

Eight requirements, R1 to R8, each marked TODO in the starter. Db, the records, Money, EnrolmentRequest, EnrolmentEvent, StudentRepository and Main are given and must not change.

  1. R1 — InMemoryStudentRepository: a second implementation of the same interface, with no database behind it
  2. R2 — H2StudentRepository: the same eight methods against H2. Watch the wasNull() trap on a nullable mark, and keep every value behind a ?
  3. R3 — RepositoryFactory.create(Store) and createDefault(): a switch expression with no default, so adding a store breaks the compile instead of returning the wrong one
  4. R4 — AppConfig: one instance, three settings read once (store, locale, export directory)
  5. R5 — FlatFee and EarlyBird: two answers from one call site and no if, with money as BigDecimal
  6. R6 — AuditLog: an observer the registry has never heard of, handing out a copy of its lines
  7. R7 — Messages and the six French keys, with one key deliberately left in English to prove the fallback works
  8. R8 — RegistryExport: write, read back, walk, glob and delete, through Path and Files

Part 2 — the suite (Session 10)

  1. A JUnit 5 suite that runs against both implementations, so one set of tests proves two stores
  2. Test data built in code, not seeded in SQL — the tests must run with no database file at all
  3. A test that fails on purpose: prove that a broken store makes the suite red, and say which test caught it
  4. An AI-generated set of test cases, each one reviewed — you keep the ones you can justify and say why you rejected the rest
The seam holds grep -rn "new H2StudentRepository" src/main/java returns hits in RepositoryFactory and nowhere else. This is the single most important line of the marking.
The interface stayed clean No import java.sql, no throws SQLException and no Connection in StudentRepository.java.
One behaviour, two stores Every test passes against both implementations. A method that works in memory and fails on H2 means the interface was written to fit one of them.
The factory carries the message create(Store) has no default; adding a third constant stops the program compiling, and you can demonstrate it.
Money is BigDecimal No double anywhere in policy/, and the promo boundary on 2026-08-31 is handled exactly.
Tests need no database The suite runs green on a machine with no data/ folder and no H2 file. If it needs one, the seam has leaked.
Tests you can trust Each test sets up its own data, asserts one thing, and fails for a reason you can name. A test that cannot fail is not a test.
The fallback is real Messages_fr.properties leaves one key out on purpose, the self-check still passes, and you can name the key and say why it is missing.
Resources are closed The Files.walk stream is in a try-with-resources and the export folder can be deleted afterwards — on Windows that is the test that catches it.
Honest use of AI Every generated test case is either kept with a reason or rejected with one. Copying a green suite you cannot explain scores nothing.

📦 What you get

  • code/a5-patterned-registry-starter — eight requirements marked TODO, plus Main (given, do not change) and SelfCheck, which reports PASS or FAIL per requirement
  • lib/h2-2.3.232.jar — the driver, vendored so the project compiles and runs offline with no download
  • lib/junit-platform-console-standalone-1.14.4.jar — JUnit 5 in one file (API, engine and launcher), vendored for the same reason, plus a src/test/java skeleton naming the four tests Part 2 asks for
  • Worked reference: code/s09-design-patterns — every technique in the session, fully commented
  • The H2 & MySQL guide, and Session 9 itself as the reading

Working with AI Tools — the Rule

⚖️
AI is a tutor, not a ghost-writer

This course teaches you to use AI tools well, so they are allowed. The line is simple:

  • Allowed: asking an AI to explain an exception message, to suggest where a resource leak might be, to review your transaction boundary, or to quiz you on a topic.
  • Not allowed: asking it to write the method, the class or the program you are handing in.

And you will be asked to defend any line in a viva. AI-generated code you do not understand is worse than no code at all, because you will be asked to explain it and cannot. A useful habit: when an AI does give you code, look for the mistake it is most likely to make in this topic — string concatenation in SQL, a catch that rolls back and then returns normally, a shared counter incremented without a lock — and check whether it made it. Catching that is a skill this course grades.

Before You Hand In — the 60-Second Checklist

✅ Every time

  • SelfCheck is green — and you ran it twice, so you know it is not luck
  • Clean build — delete target/ (or out/) and build again from nothing
  • No placeholders left — no // TODO, no throw new UnsupportedOperationException()
  • No debugging leftovers — the print statements you added to find the bug are gone
  • Every method named for what it does — calc2() is not a name
  • You can explain every line — if you cannot, delete it and write it again yourself
